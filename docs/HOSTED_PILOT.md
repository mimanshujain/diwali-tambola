# Hosted Tambola pilot

One website serves independent organizers, their guests and their party TVs. Organizers sign in with an invited Google account; guests still join with a game code and name. The Raspberry Pi setup remains the default (`HOSTING_MODE=lan`).

For a walkthrough of the host, guest and TV flows and where each environment variable belongs, see the [hosted implementation and environment guide](HOSTED_IMPLEMENTATION.md).

## What changes in cloud mode

- Each game belongs to one host. Lists, controls, tickets, claims and printing require that owner. A legacy `ADMIN_TOKEN` does not grant cloud access.
- Google sign-in uses the official Google auth library, authorization code flow, PKCE, browser-bound single-use state, nonce and signed ID-token verification. Only addresses in `HOST_ALLOWED_EMAILS` can host.
- Host sessions use Secure, HttpOnly, SameSite cookies and expire after seven days. Mutation requests require the configured Origin. Signing out revokes the current session. Removing an email from the allowlist disables its existing sessions and paired displays on the next request after the configuration takes effect.
- Guests retain private player tokens and recovery codes. Their public game snapshot excludes the roster and other players’ identities. Host approval, late-join eligibility, regeneration limits, claims and printing behave as on current main.
- A game code identifies a game; it is not an admin password or a TV credential. The final TV URL is `/tv/GAMECODE`. A new TV first opens `/screen` and enters the code generated by its host, or follows the QR pairing link. Pairing codes expire after ten minutes and work once. The resulting read-only display session lasts 24 hours and can be revoked from the host console.
- Pilot limits: five unfinished games and 100 saved games per host; 200 registered players per game, including withdrawn registrations. Creation and registration limits are enforced while holding database locks. These are guardrails, not a performance guarantee.
- Login, pairing and player recovery attempts have per-IP limits. Registration allows a larger shared-IP budget for parties. The current limiter is per process; keep the pilot at one web instance. Database-backed scheduler leases support overlapping deployments, not general multi-instance Socket.IO scaling.

## Deploy on Render

The supplied `render.yaml` describes one Docker web service and a separate managed PostgreSQL 17 database in Virginia. Both use paid compute plans. Review the current total shown by Render before creating them. Automatic code deployments are disabled so a push cannot interrupt a party.

1. Merge the hosted implementation into `main` after CI is green. The Blueprint explicitly deploys `main`; do not use the PR 13 branch.
2. Sign in to [Render](https://dashboard.render.com/), connect this private GitHub repository, and create a Blueprint using `render.yaml`. Choose an available service name and note its actual HTTPS address. If the generated address changes, update the settings below before launch. A custom domain is optional.
3. In [Google Cloud Console](https://console.cloud.google.com/auth/overview), create or select a project. Configure Google Auth Platform branding and an External audience. For the initial testing audience, add each invited organizer as a test user. Create a **Web application** OAuth client with this exact authorized redirect URI:
   ```text
   https://YOUR-ACTUAL-SERVICE.onrender.com/auth/callback
   ```
   Request only `openid`, `email` and `profile`. When using a custom domain, register that domain’s callback instead and complete any Google branding/domain requirements shown by the console.
4. Set these web-service environment variables in Render’s secret/configuration interface:

   | Variable | Value |
   | --- | --- |
   | `HOSTING_MODE` | `cloud` (Blueprint supplies this) |
   | `PUBLIC_APP_ORIGIN` | Exact HTTPS origin, such as `https://your-service.onrender.com`; no path |
   | `GOOGLE_CLIENT_ID` | Web OAuth client ID |
   | `GOOGLE_CLIENT_SECRET` | Web OAuth client secret |
   | `HOST_ALLOWED_EMAILS` | Comma-separated invited Google email addresses, including your own |
   | `DATABASE_URL` | Blueprint supplies the database’s internal connection string |

   Do not set `ADMIN_TOKEN` or use the Pi’s guest-only Cloudflare gateway for this deployment. Cloud mode needs host, guest, auth, TV and Socket.IO routes on the same HTTPS origin. TLS terminates at Render’s ingress; the app trusts exactly one proxy hop. If hosting behind a different proxy chain, review this setting and IP-based rate limiting first.
   For optional AI narration, set `GEMINI_API_KEY` and `ELEVENLABS_API_KEY` plus
   the matching `COMMENTARY_ELEVEN_VOICE_*` voice IDs on the same web service.
   See [COMMENTARY.md](COMMENTARY.md) for the Pi and Render setup. These values
   are never needed in the guest browser or TV URL.
5. Deploy manually. Startup applies additive migrations under a database lock. `/health/ready` must report a connected database. In a private browser window, confirm `/admin` asks for sign-in and an old admin key cannot unlock `/games`.
6. Use two invited accounts to create separate games. Confirm neither account sees the other’s games. Join from a guest phone, approve and submit a ticket, pair a TV, then disconnect that TV. Test a number call, pause/resume and a print preview before inviting a party.
7. Enable and verify your database backup/retention settings, test a restore to a separate database, and configure a health monitor for `/health/ready`. Verify the provider’s selected plan and recovery window before relying on it for an event.

The real Google consent flow, production hostname and Render deployment require your accounts and credentials. The automated rehearsal uses a test provider transport with real signed ID-token verification; it does not establish that your Google Console configuration is correct.

## Running a party

Hosts use `/admin` on their phones. Guests enter the code on `/` or follow `/g/GAMECODE`. Use **TV display & guest access → Pair a TV** for a separate screen. Keep the code/QR private to the display operator: the TV shows player names and claim-review tickets, but cannot mutate the game. Opening a second game on the same TV replaces its display cookie; pair it again to switch back.

Internet access is required for the hosted version. A disconnected browser retains its last confirmed board and reconnects; it does not invent calls or accept offline writes. The Pi remains the option for venues without dependable internet. Cloud and Pi instances should use separate databases.

Existing A4 printing from main is retained. This change does not import the separate game-deletion PR.

## Recovery and upgrades

Game state, tickets, call history, claims, winners, host sessions and TV sessions live in PostgreSQL, not the container filesystem. No game is recreated when an app process restarts.

In cloud mode, each scheduler holds a 15-second database lease. Its lease update, recovery and tick effects share a transaction, so a stale process cannot draw after another process takes over. A newly starting standby does not pause the active server’s games, and stopping a standby has no effect on them. Gracefully stopping the active server saves the remaining countdown and pauses games. After a hard crash, takeover occurs once the lease expires; running games then pause using the last checkpoint. The host reviews the last call and explicitly resumes. Schedule deployments between events, even with this protection.

A database failure can lose data outside the provider’s backup/recovery window. Keep independent encrypted backups and rehearse restores. The Docker build excludes backup directories, dump files and environment files; do not commit new database exports. A dump already tracked in Git history is not removed by an ignore rule.

Use a fresh cloud database for the pilot. Existing Pi games migrate with `host_id=NULL` and are deliberately invisible to cloud hosts. There is no “first user claims all games” behavior. If importing an old game is necessary, back up the source, verify the destination host’s Google identity, and explicitly assign only the selected games in a reviewed database operation.

Migration 010 is additive. Do not roll back to a pre-hosted server against a cloud database: the older server has global-key authorization. Back up before schema or deployment changes and restore to an isolated instance when investigating a problem.

```bash
npm ci
npm test
npm run typecheck
npm run build
npm install --prefix /tmp/tambola-test-tools \
  embedded-postgres@18.6.0-beta.19 playwright-core@1.64.1 @sparticuz/chromium@153.0.0
TAMBOLA_TEST_TOOLS=/tmp/tambola-test-tools node tests/hosted-rehearsal.mjs
TAMBOLA_TEST_TOOLS=/tmp/tambola-test-tools node tests/party-rehearsal.mjs
```

Use Node 26 on Linux. On ARM64, install system Chromium, omit `@sparticuz/chromium`, and set `TAMBOLA_CHROMIUM_PATH`. OpenSSL is required for the local HTTPS test ingress. Both rehearsals create disposable databases and save screenshots and logs in the printed temporary directory. The hosted suite includes signed token rejection, account isolation, CSRF, quotas, player tokens, secure cookies, TV pairing/revocation, phone/TV browser flows and two-process crash recovery. The LAN suite protects the existing party features and TV layouts.
